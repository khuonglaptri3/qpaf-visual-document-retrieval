# M2.8 — Shared real-data retrieval cache

M2.8 converts the verified full OCR corpus into one label-free, frozen retrieval
cache for both learned QARF and QPAF. It performs no learned gate training.

## Inputs and frozen settings

The active primary corpus is ViDoSeek: 1,142 queries, 5,385 pages, 292 PDFs;
M2.1-002 assigns 799/171/172 train/validation/test queries. Text, image, policy
and canonical page IDs are inherited from the verified M2.6 full OCR run.
Empty-text pages and the explicit technical-failure fallback are retained.

`configs/m2.8/cache.json` copies the three retriever settings from the calibrated
M2.2 config and pins that file's checksum. BM25 uses Unicode lowercase word
tokens, k1=1.5/b=0.75; dense uses BGE-M3, visual uses ColQwen2.5, with the
same model/base/processor revisions, float32, batch settings and 256 visual-token
budget. The approved OCR text replaces the provisional M2.2 text.

## GPU execution

One Modal A10 container executes the real corpus. CUDA is mandatory, with no CPU
fallback for neural models or their score computation. BM25 and file operations
run on the host of the same GPU container. Runtime evidence records the actual
device, CUDA/PyTorch versions, source/config/input identities and phase resources.
GPU inference uses frozen weights and disables TF32. The cap is six hours,
4 CPU cores, 32 GiB host RAM, zero automatic retries, one container per app.

The worker reads the M2.6 Volume without writing to it and reuses pinned models
from the M2.2 cache. Checked embedding and score shards persist to the dedicated
`qpaf-m28-score-cache` Volume. Same-source/config/input resume verifies checksums
before reuse. Interrupted or source-mismatched shards are never silently accepted.
The exact source used by each run is retained in its source snapshot ZIP.

## Candidate and normalization contract

All three score matrices cover all 6,149,670 query-page pairs independently.
For every query and channel, rank raw scores descending and page IDs ascending
at ties, retain top-200, then union by page ID. The union has at most 600 pages
and is serialized in page-ID order. All three real raw scores are retained for
each union member; missing/NaN/Inf values fail rather than becoming zero.

The candidate builder has no label input. It writes all four Parquet artifacts
and `candidate_freeze.json` before the finalizer accesses relevance. Min-max is
computed per query/channel over that union; ranges <=1e-15 become exact zero.
Raw and normalized cache storage is float64. **M2.4 receives raw_scores.parquet**
with exactly `query_id,page_id,bm25_score,dense_score,visual_score`; its feature
pipeline performs its own normalization. Do not feed the audit normalized file
as raw retriever evidence.

## Coverage and labels

Relevance is parsed from the hash-verified ViDoSeek annotation only after the
candidate freeze and full-array candidate replay. Coverage uses binary page
qrels and the full positive denominator, including positives outside the union.
PASS requires macro candidate recall >=0.95 and zero uncovered queries. Failures
are retained as `BLOCKED_COVERAGE`, without changing depth, injecting positives
or dropping queries. Coverage is reported per query and split; no test ranking
metric is computed. Development and test qrels are stored separately, and M2.4
loader compatibility is exercised only for train/validation records.

## Artifacts and verification

`scripts/run_m28_cache.py` supports `--prepare-only`, `--execute-prepared`,
`--status`, `--collect`, `--finalize` and read-only `--verify`.

The `bundle/` contains raw/normalized scores, channel top-lists, candidate set,
freeze manifest, coverage, separate development/test qrels, verification and
handover. Query text and frozen split IDs reside alongside it in the run folder.
The frozen M2.7 manifest is unchanged; M3 run manifests bind the real cache,
candidate and qrels hashes from the M2.8 handover.

Verification replays all portable cloud artifact checksums, requires real CUDA
and passing stage/reference evidence, checks frozen query/split identities,
reconstructs candidate ranks/union/normalization from complete raw matrices, and
checks exact Parquet schemas and M2.4/M2.5 compatibility. `--verify` never creates
missing handover evidence. The finalizer's own SHA-256 is recorded separately
from the immutable GPU source identity.

Independent human M2.10/D1 approval and learned QARF/QPAF results remain separate
downstream tasks; cache readiness is not evidence of learned QPAF improvement.
